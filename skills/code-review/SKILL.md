# Code Review 协议

## 何时使用
用户要求"审查代码 / 找问题 / 评估质量 / 检查安全隐患"时，加载本技能并严格执行。

## 工作流程（顺序不可换）

### 第 1 步：勘察项目（map before code）
禁止跳过，禁止未勘察先下结论：
1. 用 glob 列出项目根目录结构，看清全貌
2. 读 README / AGENTS.md / 依赖清单（requirements.txt / package.json 等）
3. 找入口文件（main.py / cli.py / app.py），理解程序从哪启动
4. 形成心智模型：项目做什么、模块如何依赖、数据怎么流
5. 勘察完成后，在最终报告里用一句话概括项目结构

### 第 2 步：定位审查范围
- 全仓库审查：按模块逐个进行
- 变更审查：只审变更涉及的文件（用 git diff 或用户说明定位）

### 第 3 步：逐文件审查
对每个文件按以下维度检查，每条发现必须记录证据（文件 + 行号 + 代码片段）：
1. 正确性：逻辑错误、边界条件、异常处理、资源泄漏
2. 安全：命令注入、路径遍历、硬编码密钥、不安全的反序列化
3. 可读性：命名、函数长度、重复代码、魔法数字
4. 性能：重复计算、N+1 查询、大对象常驻内存
5. 测试：测试是否存在、关键路径是否覆盖
6. 一致性：与项目现有风格和约定是否一致

## 审查结论
- 总体评价：一句话
- 严重度统计：高 X / 中 Y / 低 Z

## 问题清单
每条格式：
- **[严重度] 文件路径:行号** — 问题简述
  - 后果：为什么这是问题
  - 建议：修复方向（不直接改代码）

## 亮点
值得保持的写法（如有）

## 禁止事项
- 禁止在未完成勘察时下结论
- 禁止臆测：每条问题必须有文件 + 行号 + 代码证据
- 默认只审不改：结论写在回答里，别顺手改文件；用户明确要求修改时才动手（改前说清改哪几处）
- 禁止只报症状不报根因
